## Answers to the owner's questions

**A. Why the browser closes and reopens, and the fix.** It is one line in Sunroom Screen:
`Agent.use()` (`kiosk/agent/src/sunroom_kiosk/state.py:502-522`), which runs whenever a Sunroom is
chosen (Use This Sunroom on Where Is Your Sunroom?, the end of Run Sunroom Here, and a found
Sunroom that moved) saves the address, rewrites the browser's policy, publishes the new state,
sleeps 1.5 s and then **restarts the browser** on the new address. But the screen's own page has
already moved on by then: it hears the new state on the agent's event stream and opens the Sunroom
itself (`screen/pages/FindPage.tsx:227-231`, `HerePage.tsx:46-49`, `OpeningPage.tsx:14-22`,
`route.ts:51-54`). So the wall shows Sunroom twice: once from the page, then again from the
relaunch. A paired-screen page asks for a pairing code on every mount
(`features/display/DisplayEntry.tsx:296-329`), so a set-up Sunroom shows code A, then code B; a
fresh one shows Set Up Sunroom, then Set Up Sunroom again. A phone that typed code A in that
second and a half would even have paired a page that was just closed.

The restart was there for the browser's command line, which can depend on the address: Chromium
is told to treat a plain-`http://` Sunroom on another machine as secure
(`--unsafely-treat-insecure-origin-as-secure`, `browser.py:169-179, 222-224`), so a service
worker and Wake Lock work on the wall (PLAN §13.1). That flag is never needed for On This
Computer (`http://localhost`) nor for any `https://` address, so for those two the relaunch
changed nothing at all. And a wall run by Sunroom Screen needs neither feature before its next
restart anyway: the agent keeps the screen awake itself (`?dimmer=screen`), and the page's
updates come from a plain reload (ADR 0034). The other thing the restart guaranteed was a fresh
read of the browser's managed policy, which today names the Sunroom's origin (so the wall page may
call the agent on `127.0.0.1` without Chrome's Local Network Access prompt, `policy.py:76-82`).

The fix (T4): the agent never restarts the browser for an address. The page moves itself, as it
already does; the agent's own `navigate` through DevTools (`Page.navigate`, which exists and is
used by the watchdog) covers the one case with no page to do it (a found Sunroom that moved); the
policy stops depending on the address (an allowlist for every page in this browser, which is only
ever Sunroom: the agent's CORS admits only the Sunroom it shows, `app.py:125-158`), so it is right
from the browser's first start; and the secure-context flag takes effect at the browser's next
start, the nightly one at about 04:00 or This Screen's Restart. Nothing visible waits for it.

**B. The Discord webhook, and the public image.** Send Feedback today opens GitHub's new-issue
page with the words filled in, because the page's CSP talks only to Sunroom and "a token inside a
public image is out of the question" (ADR 0034, `features/settings/support.ts:43-47`). A Discord
webhook is such a token: its address alone lets anyone post to the channel. Three places it could
live:

| Where | What it means |
|---|---|
| **A relay the owner runs (recommended).** A small function (a Cloudflare Worker, for example, in the website's repo) holds the webhook as its own secret, takes a POST from any Sunroom, rate-limits by address and forwards the body to Discord. Sunroom's server posts to the relay's public address, which is a constant in the code like the Patreon link, and self-hosters may point `SUNROOM_FEEDBACK_URL` elsewhere or turn it off | No secret in the repo or the image; the webhook can be rotated without a release; spam can be stopped at the relay; works from every Sunroom ever shipped |
| The webhook baked into the image at build time, from a GitHub Actions secret | Breaks hard rule 1 as written ("never put into the image … tokens"); anyone can read it out of the public image; rotating it means a release, and every older image then posts into the void while telling the family "Sent" |
| An environment variable each self-hoster sets | Keeps the secret out of the image, but the owner would have to give the webhook to every self-hoster, which is the same as publishing it, and nobody non-technical would set it |

T9 builds the app's side in full against the first: `POST /api/feedback` on Sunroom's own server,
which builds the Discord message and posts it through the guarded HTTP client to the relay. The
relay's contract and a sketch are in T9 for the owner to deploy; until its address is filled in,
the form keeps the GitHub link, so nothing is broken in between. The webhook the owner pasted
with the notes goes into the relay's secret (or, if the owner chooses the second row, into the
Actions secret) and nowhere else.

**C. Rolling week as a view.** Rolling week today is a round cell beside Agenda · Hours, pressed
when on, whose icon (`CalendarRange`) is also the Week view's own icon (`ViewSwitch.tsx:10-15`,
`BoardControls.tsx:88-99`): nothing says what it does. It is also three things at once: a
household setting (Settings → Display → Rolling week, ADR 0033), each screen's own choice (ADR
0036) and a modifier of one view. As a view of its own, **Rolling Week**, it is one thing: a row in
the View menu with its words ("Yesterday, today and the five days after") and its own drawing;
each screen picks it as it picks any view, remembered as the view is; Settings → Display →
**Home view** gains it, which is the household's choice, winning over a screen's as a Home view
change does (ADR 0031); and the Rolling week switch and the cell go. Agenda · Hours stay beside
the arrows on both week views. That costs one migration (T8): the home view `rolling` and the end
of `display_rolling_week`, with households that had it on moved to the Rolling Week home view.

The header gains room, which was the point: at 1920 Standard the four view icons with the chosen
word took about 340 px and the Rolling week cell 72 px with its gap; one View button with the
icon, the word and a chevron takes about 190 px. The worst case of ADR 0033 and 0036 (Wed, Sep 30,
12:30 PM, four people filtered, the live icon showing) now fits on one row with room to spare.

**D. Rotation on a computer.** This Screen already has Rotation (Landscape, Portrait left or
right, Upside down) on a Raspberry Pi, where the agent turns the picture with `wlr-randr` or
`xrandr` and keeps touch aligned through labwc (`platform/pi.py:142-176`); on a computer the row
is hidden, because "its own display settings do that" (`platform/base.py:237-239`). The owner's
case is a monitor mounted on its side that the computer doesn't know about. Two ways were weighed:
the page turning itself (a CSS rotation of the whole app) and the display turning (what the Pi
does). The page way works on every system but would have to remap every drag, swipe and scroll
from the screen's axes to the page's, and the browser's own scrolling inside a rotated box is not
something to bet a wall on; so T6 turns the display, system by system: Windows through its display
settings API (no administrator needed), Linux desktops through `wlr-randr` or `xrandr` as the Pi
does (with the output found by the agent when the installer didn't name one), KDE through
`kscreen-doctor` where it is there, and a Mac, which has no public way to turn a display from a
program, keeps the row hidden and KIOSK.md says where to turn it (System Settings → Displays). The
household's dormant `display_orientation` field (stored, unread since M0) stays as it is.

**E. "Kitchen screen", the default name.** A paired screen is called "Kitchen screen" until it is
named (`backend/src/sunroom/auth/schemas.py:104, 109`, `meta/setup.py:42`,
`features/phone/PairCode.tsx:22`, `DisplayEntry.tsx:388`), and the word is in about 250 places
besides: the installers' every line, the README, the service and desktop entries, PLAN, UX, code
comments. T2 makes the default **"Wall screen"** (the app describes itself as a family wall
calendar, and a wall is not a room), keeps Kitchen as the first *suggestion* in Name This Screen
(a suggestion is not an assumption), and says "the screen", "a Sunroom screen" or "the display"
everywhere else. Screens already named keep their names: a name is a name.

        let body;
        try { body = JSON.parse(text); } catch { return new Response(null, { status: 400 }); }
        if (!Array.isArray(body.embeds) || body.embeds.length !== 1) return new Response(null, { status: 400 });
        // a rate limit by request.headers.get("cf-connecting-ip") goes here (a KV counter, or Cloudflare's rate-limiting binding)

## Not chosen, and later

- **The page turning itself (a CSS rotation) for Rotation on a computer.** Every drag, swipe and
  scroll would need remapping between the screen's axes and the page's, and the browser's own
  scrolling inside a rotated box is not something to bet a wall on. If a Mac on its side turns
  out to matter, it is the way to revisit, with `display_orientation` (stored, unread) as the
  household's part of it.
- **The agent as a reverse proxy for Sunroom** (the browser would show
  `http://127.0.0.1:7800/`, a secure context with no Local Network Access, no secure-context flag
  and no CSP widening for `?screen=`). Elegant, and a batch of its own: event streams, uploads,
  the Host rule and the cookie's name all pass through it.
- **"Remote Connection"** as the second card's name: "remote" is a technician's word (UX §2);
  "Connect to a Sunroom" says the same in the family's.
- **"Sunroom URL"** as the field's label, for the same reason (UX §4: the screen's pages never say
  URL); "Sunroom address" with two examples under it.
- **Cancel on the household's sheets** ("Keep It", "Keep This Copy", "Keep Everything" in
  Backup): they say what happens, which is the rule for buttons; the owner asked for Cancel on
  This Screen's Shut Down, and its sibling sheet follows for the page's sake. If the owner wants
  Cancel everywhere, it is a one-line rule change in UX §2 and a sweep.
- **Renaming signed-in devices** in Settings → Devices: a device's icon comes from its name; a
  later batch can give devices a kind of their own.
- **The feedback relay's own repo and deployment**: the owner's, beside the website
  (`../sunroom-site`), with its secret in the host's secret store; this repo holds only the
  app's side and `FEEDBACK_URL`.
- **An email from the feedback form**, or a reply channel inside the app: the optional "How to
  reach you" is as far as this goes; Sunroom has no account to reply to.
- **Dropping the dormant `display_orientation` column**: a future migration, when the field's
  fate is decided.
