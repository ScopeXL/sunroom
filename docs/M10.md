# M10: languages, and a screen that sets itself up again, as tasks

Sunroom 0.17.0 is on the owner's wall and devices. The owner's notes of 2026-10-30 ask for two
things. First, **language support**: not a translation, but the file tree, the runtime, the
setting and the checks that let the app be translated, with English the default and every word
the family sees moved out of the code and into one English file, so that each later change keeps
the languages whole. Second, a screen that **updates its own setup** on a Mac, Windows or Linux
computer: when a release changes how Sunroom Screen loads or runs, its dependencies or anything
else the installer puts in place, the family taps Update, confirms, and the screen reinstalls
Sunroom Screen (and Sunroom itself, when it runs on that computer), keeps every setting and the
pairing, restarts the computer if that is needed, and comes back as it was.

And one small thing M9 left waiting for the owner's relay: Send Feedback's address (T17).
This file turns all of it into tasks for the Opus 5.5 session that builds them (PLAN §15,
**M10 → 0.18.0**). It was written on 2026-10-30 from a read of the code at `044f1fb` (v0.17.0);
line numbers are from that commit and may drift a little.

**Where this file lives.** `docs/M10.md`, beside `docs/M9.md` and the earlier batches, committed
as `docs: M10, languages and a screen that sets itself up again, as tasks` (T0).

**What the owner settles before T1** (each has a default, so the build can start; the owner
changes any of them by editing the Decisions table):

1. **How the words are kept and found.** The recommendation is row 5 of "The options" below:
   plain ICU JSON files under `lang/`, formatted by one small library, with Sunroom's own thin
   layer around it, checked by the type checker, a lint rule and `just lang`. The runners-up are
   there with their trade-offs. Built as recommended unless the owner picks another row.
2. **Linux and Raspberry Pi screens installed before 0.18.0 need the one-command installer
   once more**, in a terminal, so their root helper learns to apply a release's system files
   (T11). Macs and Windows computers need nothing. After that, every update runs from the screen.
   The CHANGELOG says so.
3. **One Update for everything on that computer.** Update Now (and the overnight update) brings
   Sunroom Screen, its setup, and the Sunroom that runs on that computer (as a program, or an
   all-in-one Pi's Docker Sunroom) to the release; **Update Sunroom Too** goes. A **Reinstall…**
   does the same at the version already installed, for a screen that misbehaves.
4. **A language shows in the picker only once its file is complete.** `lang/es.json` ships as
   the placeholder the owner asked for, marked `preview` in the registry, invisible to families
   until someone translates it (docs/LANGUAGES.md says how; it is not this batch's job).

## Answers to the owner's questions

**A. How other self-hosted apps handle translations.** The pattern that every mature project
converged on is the same, whatever the library: one source file of English words in the
repository, keys (or the English sentence itself) in the code, a translation platform that reads
the source file and sends the other languages back as pull requests, and checks that keep the
source and the code in step.

| App | Source of truth | In the code | Other languages come from |
|---|---|---|---|
| Immich | one English JSON file in the repo | `$t("key")` (svelte-i18n) | Weblate's hosted server, about 70 languages, each sent back as a pull request |
| Jellyfin (web) | one English JSON file per app | i18next keys | Weblate (translate.jellyfin.org) |
| Home Assistant | `strings.json` per integration, and the frontend's English file | keys | Lokalise, uploaded after a merge and pulled back on a schedule; developers compile the local copies with a script |
| Mealie, Paperless-ngx | JSON (Vue) or XLIFF (Angular) English files, plus gettext `.po` on the Python side | keys, or gettext calls | Crowdin |
| Nextcloud, Grocy, Tandoor | gettext `.po`/`.pot` and JSON | gettext calls | Transifex |

Three things they share are worth copying: the English file is the only place the words live;
the checks run in CI (missing keys, unused keys, placeholders that differ between languages); and
a *pseudo-language* (every word made visibly foreign and 40 % longer) is how teams find the words
that slipped past the system and the boxes that are too small. Two things differ: whether the
code holds a key (`settings.language.title`) or the English sentence (`"Choose a language"`) as the
message's id, and whether the Python side has a runtime of its own (gettext) or none.

**B. The options.** Five ways to do it, judged against this app: one page for two shells plus
the screen's own pages (React, Vite, a strict CSP that forbids runtime styles), a FastAPI server
and a Python agent that both say sentences the family reads, AI sessions as the maintainers (who
must find every word and never miss one), and a family who reads the words from across a room.

| | How it works | For | Against |
|---|---|---|---|
| 1. **react-i18next** (JSON resources, keys) | `t("settings.language.title")`; `en.json` per language, loaded as chunks; plurals by key suffix (`_one`, `_other`); `{{name}}` placeholders; keys typed by declaring the English resource's type | The most used; `eslint-plugin-i18next` (which works with any runtime) and `i18next-parser` exist; translators know the JSON | A provider and a hook per component; its plural convention and `{{}}` syntax are its own, so the server would re-implement them for its fallbacks; typed keys over a 1,300-key file are known to be slow for `tsc`; three new dependencies for what is, underneath, a lookup and a format |
| 2. **FormatJS / react-intl** (ICU, messages defined in the code) | `<FormattedMessage id=… defaultMessage="Choose a language" />`; `formatjs extract` writes `en.json` from the code; `formatjs compile` builds each language | ICU MessageFormat (the standard translators and platforms speak); strong lint rules (`enforce-default-message`, `enforce-placeholders`) | The English stays in the code and `en.json` is generated, the opposite of what the owner asked; an extract-and-compile step in every build; the heaviest runtime of the five |
| 3. **Lingui** (`<Trans>`, `.po` catalogs) | `<Trans>Choose a language</Trans>`; the English sentence is the id; `lingui extract` writes `.po` files, `lingui compile` the runtime catalogs; a Babel or SWC macro plugin | The most readable JSX of all; gettext `.po` is what Weblate, Crowdin and Poedit were built for; ICU under the hood | Again the English lives in the code; a compiler plugin in Vite's React plugin; a `.po` toolchain the Python side would share only by adding gettext there too |
| 4. **Paraglide JS** (inlang) | `messages/en.json`; a compiler turns every message into a typed function, `m.settings_language_title()`; a Vite plugin recompiles on change; unused messages tree-shake away | The strongest type safety (a wrong key is a compile error, a wrong parameter too); the smallest runtime; no provider | Generated code in the tree (gitignored, built in CI); its own message format (not quite ICU, with variants of its own) the Python side would have to parse; a young project whose 1.x → 2.x broke its API, which an AI-maintained app must re-check at every bump |
| 5. **Plain ICU JSON, one formatter, Sunroom's own thin layer** (recommended) | `lang/en.json`, flat keys, ICU messages (`{name}`, `{n, plural, one {# day} other {# days}}`), formatted by `intl-messageformat` (FormatJS's core, used alone: a parser and a formatter, no React, no styles); `lib/lang.ts` (about 150 lines) holds the current language in the existing store, `t(key, params)` and `useT()`, typed keys from the English file's shape, the lazy load of a language's chunk, the pseudo-language transform; the server and the agent read the same English file for their fallback sentences and send *keys and parameters* to the page, which speaks the family's language | Exactly what the owner described: the words in files, keys in the code; one runtime that speaks (the page), two that only name keys (the server, the agent); ICU for translators; nothing generated and nothing compiled; the checks are the type checker, one lint rule and one script; precedent: the keyboard (ADR 0022) and the recurrence engine (ADR 0023) are Sunroom's own where a library's shape didn't fit | Sunroom owns the glue (a store, a hook, the lazy load, the fallback, about 150 lines, all tested); no translation platform integration out of the box (none of the five has one; Weblate reads flat ICU JSON as it is) |

**The recommendation is row 5.** Row 1 is the respectable alternative if the owner would rather
stand on a library's conventions than Sunroom's; the tasks below are written so that swapping the
formatter for i18next in T1 changes `lib/lang.ts` and the key syntax, nothing else. Rows 2 and 3
put the English back into the code, which the owner ruled out; row 4's compiler and format are
more than this app needs and more than an AI session should have to re-learn at each release.

**C. Why the server and the agent send keys, and only the page speaks.** The words a family reads
come from three programs: the page (about 1,200 literals today across `frontend/src`, the screen's
own pages included), the server (123 `AppError` sentences, the Needs Attention sentences, each
plugin's name, description, room and settings labels, the repeat sentence `recurrence.describe`
writes) and Sunroom Screen's agent (its toasts, refusals and progress steps, about 36). Giving
each a translation runtime of its own would mean three formatters, three loaders and three ways
to be wrong. Instead: the server and the agent keep speaking English (from the same `lang/en.json`,
so no English stays in Python), and every sentence they send also carries its **key and
parameters** (`{"error": {"code", "message", "key", "params"}}`; a problem's `key` and `params`
beside its `title`; a plugin's names found by the page under `plugins.<id>.…`; the repeat rule as
a structure the page words itself). The page formats the key in the family's language and shows
the English only for a key it doesn't know (an older page after an update). The household's
language is a setting on the server, read by every page; a later per-device override is a
page-side change only.

**D. Why "reinstall in place", and what "firmware" means here.** Today an update replaces one
thing: Sunroom Screen's wheel (`updater.py`, `apply.py`). Everything the installer put around it
stays as the day it was installed: the user service or LaunchAgent or Startup shortcut, labwc's
autostart block and window rule, the browser's policy and the root helper that writes it, the
Wi-Fi and backlight files, the packages. So a release that changes how the screen starts, what it
runs on, or what the helper may do can't reach a screen already installed, and the only fix is the
one-command installer in a terminal, which a family at a wall can't type. The owner's "update the
firmware" is exactly this gap. Taking the words literally (uninstall, then install) would be worse
than it sounds: the uninstaller's default deletes the browser profile that holds the pairing, the
screen would be dark for minutes, and a failure halfway leaves nothing to come back to. What the
family needs is the *end state* of a fresh install with their settings kept, which is what a
rerun of the installer already promises ("the files it owns are rewritten with the same
content"). So this batch makes Sunroom Screen able to do that rerun itself, without a terminal:

- **Sunroom Screen carries its own setup.** The templates in `kiosk/files/` go into its wheel
  too, and a new command, `sunroom-kiosk setup`, renders each file the installer owns for this
  user from this version's templates and this screen's settings, compares, and rewrites what
  differs: the user unit, the LaunchAgent, the Windows start-up entry, the labwc block and rule,
  the XDG autostart, the helper copies, the settings file (migrated to this version's keys), the
  install-state the uninstaller reads. It runs after every update (in the apply step, before the
  new version starts), at every start (so a file someone broke heals itself), from
  **Reinstall…**, and on the installers' first install (T14), so there is one way to set a screen
  up and it is Sunroom Screen's.
- **The system's part, on Linux and a Pi, through the root helper.** The helper gets one new verb,
  `apply-system WHEEL`: it fetches that release's `SHA256SUMS` from GitHub itself, checks the
  wheel against it, and only then takes the system files out of that wheel (the Wi-Fi and
  backlight files, the i2c module, the sudoers rule and the helper's own next version, last) and
  installs what the wheel's package list says is missing. Nothing root-run ever comes from a file
  the user could have changed: the trust root stays what it has been since 0.13.0, GitHub's
  Releases over HTTPS and their checksums. (The installer's own download of `kiosk/files` is
  pinned by tag but not checksummed; the helper is stricter.) A helper from 0.17.0 doesn't know
  the verb, hence decision 2: the one-liner once more on those screens.
- **One update does everything on that computer.** Sunroom Screen, its setup, the system's part,
  then the Sunroom that runs there (as a program: `look_after_local` already brings it to the
  agent's version at start; an all-in-one Pi's Docker Sunroom: `update.sh` through the helper, as
  Update Sunroom Too did), with progress in the Software row and a result when it is back.
- **A restart only when the setup says so**: the labwc block, the window rule, the kernel command
  line, a group membership or a desktop package changed (a Pi, or a Linux desktop); never on a
  Mac or Windows, where the agent restarting itself is enough. The screen says it is restarting
  the computer, and says "Updated to 0.18.0" once it is back.
- **Nothing is lost.** The browser profile (the pairing) is never touched; the settings file is
  migrated, never recreated; the install-state keeps its format; the family's data belongs to
  Sunroom, which backs up its database before any migration at its own start; the agent copies
  its own small files aside before an update, and the previous wheel comes back when the new
  version doesn't answer, as today.

**E. What stays English, by design.** The installers' and uninstallers' terminal output and the
`sunroom`/`sunroom-kiosk` commands (the self-hoster's tools); the logs; the Discord message Send
Feedback posts (the project's channel; what the family typed goes as typed; the relay checks
every part of it, so `core/feedback.py` never changes: T17); the docs and the
CHANGELOG; the names Sunroom, Sunroom Screen, Discord, Apple, Google. Everything a family reads on
a wall, a device or the screen's own pages goes through `lang/`.

### The sweep's recipe (T2 to T6 share it)

1. Open the file. Every literal the family can read is a key: JSX text; the `aria-label`,
   `placeholder`, `alt`, `label`, `hint`, `title`, `name`, `text`, `act`, `keep`, `action` and
   `submit` props of components; `showToast(…)`'s words; an `Error`'s message that ends in a
   toast; tables of words (`FOUND_WORDS`, `ROTATIONS`, `UPDATES`, `backupWords.ts`,
   `screensaver/words.ts`, `TIPS`); a plugin room's `label`; a Settings page's `title`. Pick the
   key by the convention in Decisions, add it to `lang/en.json` (`just lang --fix` sorts the
   file), and replace the literal with `t("key")` (in a component, `const t = useT()` so it
   re-renders when the language changes; in a mutation's callback or a formatter, the module's
   `t`, which reads the language at that moment).
2. A sentence built from pieces (`` `${name}'s calendar` ``, `"Not saved — " + why`) becomes one
   message with placeholders: translators need whole sentences, and word order differs. A count
   becomes a plural (`{n, plural, one {# day} other {# days}}`). A choice of words becomes a
   select, or two keys.
3. A table whose entries are picked by a code (a plugin's id, a color, a tip, a view) uses the
   typed helper for that family (`tPlugin(id, "name")`, `tFamily("ui.colors", color)`), never a
   template literal cast to `Key`: `just lang` knows the families and checks every member.
4. Tests keep their English literals (they run in English; `en.json` loads synchronously). A
   test that checked a word table reads the value from `en.json` instead.
5. Take the folder out of the lint's ratchet in `eslint.config.js` and run `just quick`, then
   `just lang`: a key that nothing uses fails (so a key is added as it is used, never ahead).
6. Note what surprised you in `docs/GOTCHAS.md`, "Languages".

  already reads `localStorage["sunroom.language"]` first; a row in Settings → Devices, or in

- **Right-to-left languages and other scripts.** The registry has `dir`; nothing sets a
  right-to-left layout yet (the rail's side, the board's columns, the keyboard), and Lexend has
  no Arabic, Hebrew, Cyrillic or CJK glyphs: a fallback face, loaded only for such a language.
- **A translation platform.** Weblate's hosted service is free for open source and reads flat
  ICU JSON as it is (Immich and Jellyfin live on it); worth setting up the day a contributor
  asks, not before. Until then, a pull request with a file.
- **Machine translation inside the app, or at build.** A session translates with the glossary
  and a person reviews; nothing automatic ships.
- **The installers and the commands in another language.** They speak to the self-hoster who
  typed a command; English stays.
- **react-i18next, Lingui, FormatJS, Paraglide.** Answer B. T1 keeps the formatter behind
  `lib/lang.ts`, so a later swap touches one file.
- **An update started from a device** (a phone telling a screen to update). The agent listens
  on the screen's own computer only; a relay through Sunroom's server is a batch of its own,
  with the reverse-proxy idea M9 left for later.
- **A "What's new" sheet** from the CHANGELOG before an update: it would need GitHub from the
  screen; the CHANGELOG link in Help is enough for now.
- **Managing an all-in-one Pi's Docker Sunroom files** (`/opt/sunroom`) from the screen: they
  stay the installer's and `update.sh`'s.
- **Literally uninstalling and installing again** for an update: Answer D.
- **A GUI root prompt (polkit) on a Pi** for the first 0.18.0 update: there is no keyboard to
  type a password into on a wall; the one-liner once is honest.
- **Dropping the dormant `display_orientation` column**: still a future migration (M9's note).
