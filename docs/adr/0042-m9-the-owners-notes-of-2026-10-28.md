# ADR 0042: The owner's notes of 2026-10-28 (M9)

- **Status:** Accepted
- **Date:** 2026-10-28

## Context

- Sunroom 0.16.1 went on the owner's wall and devices, and Sunroom Screen was tried on Windows, a
  Mac and Linux. The owner's notes of 2026-10-28 were fifteen, in four groups: the Calendar's
  header (the views in one menu, Rolling week as a view of its own, Week with Hours by default);
  the screen's first setup (the choice cards, the address check, the browser that closed and
  reopened, the wizard's words); This Screen and Devices (the network row, the address, updates
  overnight, Shut Down's words, rotation on a computer, Uninstall, renaming screens); and the
  project around the app (no more Sunroom OS, no more "kitchen screen" or "phones" where any device
  is meant, a Discord, and feedback that needs no account). `docs/M9.md` turns them into tasks,
  answers the owner's questions and records every decision; this ADR keeps the ones that change an
  earlier decision or that a later session would otherwise have to rediscover (PLAN §15, M9 →
  0.17.0). It was started with the batch's first task and gained a row with each task after.
- The owner settled the plan's open questions on 2026-10-28: Sunroom OS is deleted, not hidden;
  the Discord webhook lives in a relay the owner runs, which this batch also writes for the owner
  to deploy (never in the repo or the image); and Week with Hours is the default for new
  households only.

## Decision

| Question | Decision |
|---|---|
| Sunroom OS | **Retired, and deleted** (changes part of ADR 0035): `kiosk/os/` (the pi-gen stage, `build.sh`, `imager.py`, the boot splash), its workflow and `docs/SUNROOM-OS.md` are gone, and with them the agent's paths for it: the platform's `sunroom_os` and `update_system`, the Pi's Docker `run_sunroom` (and `PullProgress`, and `stream_command`, which only it used), the updater's restart on `/run/reboot-required`, the root helper's `apt-upgrade` and `run-sunroom`, and `sunroom_os` in the agent's state. A Pi is a Linux computer set up with the installer on Raspberry Pi OS: On This Computer runs Sunroom there as a program, as on any computer (ADR 0038), and `--with-sunroom` (Docker on a Pi) stays, updated through the helper's `update-sunroom`. **Connect to Wi-Fi first** is no longer Sunroom OS's: any screen with no network that can join Wi-Fi goes there before either way. **Updates are Install overnight by default on every screen** (it was Sunroom OS's default alone; a screen whose Updates was set to Off keeps Off). The 0.16.1 Release keeps the last image, and Raspberry Pi Imager's Sunroom entry stops updating; git history keeps the build. The pretend platform keeps `run_sunroom`, the stand-in for local.py under `--fake` |
| The screen's name, and devices | **A new screen is "Wall screen"** until it's named (`KioskPairIn`, `KioskPasswordPairIn`, setup's `SCREEN_LABEL`, the pair sheet and the wall's password pairing; Pair's toast names what the server answered); Name This Screen's suggestions stay Kitchen, Hallway, Living room, Office, then Other (a suggestion is not an assumption), but **none is chosen at first** (Kitchen was, so a tap on Done named every screen "Kitchen screen"; the plan missed it): Done with no place picked keeps "Wall screen". Screens already named keep their names. **No "kitchen" where the screen is meant** in the app, the installers, the service and desktop entries, the README and the docs (the batch plans, ADRs and released CHANGELOG are history). **"Device" wherever any device is meant** (changes part of ADR 0034's examples): "Who's Using This Device?", "every device signs in again", "the address you open on your other devices", Pair a Display named by its place on any device (Settings → Devices, under More on a phone), the wall's second setup card **On Another Device**. "Phone" stays where a phone is meant: scanning a QR code, installing the app on a phone's home screen, the phone shell's own lines, a device's detected kind ("Sign Out of This Phone"), and a phone on mobile data. UX §2 "Devices and screens" says the rule |
| The screen's first page | **One choice, then Continue** (changes part of ADR 0038): `ui/Choice` gains a chooseable form inside a `ChoiceGroup` (`role="radiogroup"` named by the question): the whole card is one `role="radio"` button, a 2 px line border at rest, a 3 px ink border and a `CircleCheck` in `text-sun-ink` in its corner when chosen (its padding a pixel less, so nothing inside moves), the arrow keys, Home and End move the choice and only the chosen card is in the tab order; the plain form (a section with its own button) stays for Set Up Sunroom on the wall, whose second card is a QR code. **On This Computer** ("Run Sunroom right here.") is chosen from the start where the screen can run Sunroom; **Connect to a Sunroom** ("Your family already runs Sunroom somewhere else.") replaces On Another Computer ("Remote Connection" would be a technician's word), chosen when it's alone; **Continue** (primary, centred) goes the chosen way, through Connect to Wi-Fi first as before. **The address**: **Sunroom address** (the screen's pages never say URL), empty at first (the check tries both schemes), with two examples in its hint; checked when the field is left or submitted with a changed address, never an empty one or a scheme alone (a tap on Check Address blurs the field first, so the same address already on its way isn't asked twice); **Check Address** shows Checking… (`aria-busy`), **Found** (a check, an ink border) or **Not Found** (an ✕), back to rest on typing; **Use This Sunroom** rises into the same row at the right (`rise-in`, instant under Reduce Motion). The "Still looking…" line of On Your Network moved inside its list item (axe: a list holds list items only; the item had `role="status"`) |
| The browser that closed and reopened | **The agent never restarts the browser for an address** (changes part of ADR 0035 and 0038). `Agent.use()` saved the address, rewrote the policy, published the state, slept 1.5 s and restarted the browser on the new address, while the page that chose it had already opened Sunroom on hearing the state: the wall showed Sunroom twice (a paired Sunroom's code A, then B; a fresh one's Set Up Sunroom twice), and a device that typed code A in between paired a page that was just closed. Now `use()` and `forget()` save, write the policy and publish, and return; **the pages move themselves** (Welcome, Find, Here and Opening already did; the wall's This Screen, after Change Address, toasts "Address changed. Looking for another Sunroom…" and opens the agent's own Find page a moment later, `openScreenPage`), and **a found Sunroom that moved**, the one case with no page to move, is opened in the page already there through DevTools (`Supervisor.navigate`, `Page.navigate`; a restart only when DevTools doesn't answer). **The policy names no Sunroom**: `LocalNetworkAccessAllowedForUrls: ["*"]`, every requesting site, a value the policy's own documentation lists (Chrome since 139; it still applies to loopback requests beside Chrome 146's `LoopbackNetworkAllowedForUrls`, which isn't used because a Linux screen's installed root helper refuses keys it doesn't know). That's safe because this browser only ever shows the chosen Sunroom, the agent's CORS answers no other origin and the wall's CSP opens nothing else; the policy is right from the browser's first start, written at install and at every start as before; `sunroom-kiosk policy --url` is still taken, and ignored. **The secure-context flag** for a plain-http Sunroom on another machine stays on the command line, read at the browser's next start (the nightly restart, This Screen's Restart, a sign-in); Chromium's `OverrideSecurityRestrictionsOnInsecureOrigin` policy needs a restart too, so it isn't added. Nothing on a wall run by Sunroom Screen needs it before then (the agent keeps the screen awake; updates come from a plain reload) |
| Setup's words | The aside: "You can change all of this later in Settings." (no "About three minutes"). Welcome: "Let's set it up. It takes a few minutes, and you can change all of it later in Settings."; Set Up Here's card the same. **All Done!** ends setup (it was You're Set): on a device "Sunroom is ready for your family.", **Open Sunroom** as the page's one big button, and one quiet line under it, "Everyone at home signs in with the household password." (the paragraph on pairing a screen goes; Devices says it); on the wall the QR code, "Scan this with a phone to add it, or open sunroom.local on any device, then sign in with the household password." and Open Sunroom. The design rules take "All Done!" as Title Case (a trailing mark is not a word). The chosen Welcome card's check is drawn as All Done!'s (`fill-sun text-on-sun`) |
| This Screen's Network row | **The connection only**: `networkWords` and **Change Wi-Fi** where the screen joins networks itself; **Open Network Settings** goes from This Screen and Can't Reach, and with it the capability `open_network_settings`, the route `POST /api/screen/open-network-settings` and each adapter's opener (18 routes now). **A Mac reports its connection** (it had no `network()`, so a Mac on Wi-Fi said Wired): the default route's interface (`route -n get default`), Wi-Fi when that's the Wi-Fi port (`networksetup -listallhardwareports`), else wired; the network's name from `networksetup -getairportnetwork` when macOS says it, which since macOS 14.4 it does only to a program with Location access (tried on the build Mac, macOS 26: "You are not associated with an AirPort network." while on Wi-Fi, and `ipconfig getsummary` shows `<redacted>`), so a Mac mostly says "Wi-Fi: connected"; no signal strength. **Windows** keeps reading `netsh wlan show interfaces`, which since Windows 11 24H2 answers only with Location access on: without it a Wi-Fi screen says Wired (KIOSK says where to turn it on; reading the adapters through `GetAdaptersAddresses` would fix it, a follow-up) |
| This Screen's Address row | **Where Sunroom runs**, not how it was found: `local` "on this computer", `discovered` and `typed` both "on another computer" ("typed" was a technician's word); a found Sunroom gets the row's hint "Found on your network: this screen follows it if its address changes.", the one behaviour that still differs (`Agent.refind`). Change Address's sheet keeps its words and gets **Cancel** for "Keep This One", here and on Can't Reach, so the page's two questions (with Shut Down's, T6d) end the same way; the household's sheets keep their "Keep …" buttons (UX §4 Backup) |
| Updates overnight | **Install overnight is every screen's default** (it was Sunroom OS's alone; T1 made `update_check()` answer `nightly` when nothing was chosen): at the start of the household's sleep hours the agent installs a new release of itself, and Sunroom with it where Sunroom runs on that computer, with the previous version back when the new one doesn't start. A screen whose Updates was set to **Off** keeps it (the config's `SUNROOM_UPDATE_CHECK=off`); an empty value, which every installer wrote, now means overnight |
| Shut Down's words | **Shut Down This Screen?**: "This turns off the computer this screen runs on. It stays off until someone turns it on again." **Shut Down** (danger) · **Cancel** (it was "It stays off until it's unplugged and plugged back in." with **Keep It On**: a Pi's words, and a computer isn't unplugged to start it) |

## Consequences

- No schema change from Sunroom OS. The agent's state (`GET /api/screen`) loses `sunroom_os`
  (`screen-openapi.json` and its types); the root helper's usage is `write-policy PATH |
  update-sunroom`; `just kiosk-image` and the release's Sunroom OS run are gone (RELEASING, the
  deploy skill).
- No schema change from the words: the API's defaults for a screen's label are "Wall screen"
  (`openapi.json`); a screen's row keeps whatever name it has.
- No schema change from the first page. New in the frontend: `ChoiceGroup` and `Choice`'s `value`
  (`ui/Choice.tsx`); `FindPage`'s `CheckFace` and `unfinished`.
- No schema change from the browser's restart. The agent's policy document takes no address
  (`policy.document()`, `EVERY_SITE`); `refind()` navigates; the frontend's `openScreenPage`.
