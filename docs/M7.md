# M7: Sunroom Screen, the OS image, one-command installs and This Screen (plus two wall fixes)

Sunroom 0.12.0 is on the owner's wall and phones. On 2026-10-20 the owner asked for two small
wall fixes and for a plan: research a "full page OS" the family can flash, an overlay on the
kiosk app for the device's own settings, and one install command per OS that ends on a page
which finds Sunrooms on the network. This file is that plan, written from a read of the code at
`4ab789f` (v0.12.0); line numbers are from that commit and may have drifted a little. It is for
the Opus 5.5 session that builds it. Nothing in it is built yet.

**Where this file lives.** `docs/M7.md`, beside the M6 batches, committed as
`docs: M7, Sunroom Screen, planned`.

## Why

Three asks from the owner on 2026-10-20, designed here from a read of the code at `4ab789f`
(v0.12.0):

1. **Keyboard.** The wall's on-screen keyboard shows a number row above the letters. Drop it; the
   existing "123" key reaches the numbers.
2. **Now line.** In the calendar's Hours view the current-time line draws over the day-of-week
   head at the top of today's column. It should float only over the events.
3. **A Sunroom OS, and one command per OS.** Research a "full page OS" a family can flash: it
   boots straight into Sunroom as a kiosk, yet the device itself (restart, shut down, update,
   network, screen) is managed from an overlay on the app, the way a phone's settings sit over
   its apps. Linux, a Raspberry Pi at minimum, touch. Keep the kiosk path for an existing Linux,
   macOS or Windows machine, but make it one command (`curl -fsSL …/install.sh | bash`, and the
   same for the other two), ending on a landing page that finds Sunrooms running on the network
   or takes a typed address. The typed address is what a future hosted Sunroom will hand out.

The two fixes are **batch 0**, a patch. The rest is milestone **M7, "Sunroom Screen"**, in two
batches, each a minor release. Batch 1 builds the pieces that work on today's Pi install (a small
agent that supervises the kiosk browser, setup pages in Sunroom's own design system, a parent-only
**This Screen** page on the wall, a discovery route on the server, GitHub Releases); batch 2 adds
the flashable Raspberry Pi image, "Run Sunroom on this screen", and the macOS and Windows
installers.

## What exists (and what the request assumed differently)

- **The Pi kiosk is already a one-liner.** `curl -fsSL https://raw.githubusercontent.com/ScopeXL/sunroom/main/kiosk/install.sh | bash`
  (README lines 37 and 73; `docs/KIOSK.md`). `kiosk/install.sh` (1850 lines of bash) has three
  modes: everything on one Pi (Docker from `get.docker.com`, Sunroom in `/opt/sunroom`), only
  the screen (`--display-only --url …`), or only the server. Options: `--rotate`, `--output`,
  `--force-hdmi`, `--brightness auto|ddc|sysfs|none`, `--no-screen-helper`, `--x11`,
  `--version`, `--port`, `--no-reboot`, `--uninstall`. It refuses to run as root and asks for
  `sudo` itself; running it again is safe. `KIOSK_VERSION` in it equals `VERSION`
  (`scripts/release.py`, `scripts/check_release_meta.py`).
- **A launcher and a helper, as user services.** `kiosk/sunroom-kiosk` (bash) waits for the
  desktop, the clock and `/api/health`, then execs Chromium with the kiosk flags
  (`sunroom-kiosk:231-258`: `--kiosk --start-maximized --no-first-run --noerrdialogs
  --disable-infobars --hide-crash-restore-bubble --touch-events=enabled --disable-pinch
  --overscroll-history-navigation=0 --enable-features=OverlayScrollbar
  --disable-features=Translate,TranslateUI --password-store=basic --disable-component-update
  --check-for-update-interval=31536000 --autoplay-policy=no-user-gesture-required`, plus
  `--ozone-platform=wayland --enable-wayland-ime --wayland-text-input-version=3` on labwc, and
  `--unsafely-treat-insecure-origin-as-secure=<origin>` for a plain-http Sunroom elsewhere) on
  `<url>/display?dimmer=screen|page`. The profile `~/.config/sunroom-kiosk/profile` holds the
  pairing cookie. `kiosk/sunroom-screen` (Python, standard library) long-polls the public
  `GET /api/display/state?wait=55` and switches the panel off and on (`wlopm`, `wlr-randr`,
  `xset`, or a backlight's `bl_power`) and sets brightness (sysfs or `ddcutil`). Units:
  `sunroom-kiosk.service`, `sunroom-screen.service`, and a 03:55 restart timer. The URL lives in
  `~/.config/sunroom-kiosk/config` (`SUNROOM_URL`, `SUNROOM_SESSION`, `SUNROOM_OUTPUT`,
  `SUNROOM_ROTATE`, `SUNROOM_SCREEN_HELPER`, `SUNROOM_BRIGHTNESS`, `SUNROOM_DDC_BUS`,
  `SUNROOM_BACKLIGHT`, `SUNROOM_MODE`). `kiosk/labwc-rule.py` hides the pointer and turns on
  real touch events in `rc.xml`. No sudoers file exists; privileged work happens at install time.
- **The server already has a command channel to screens.** `POST /api/kiosk/command {reload |
  wake | screensaver | show_event}` (parent) publishes the `kiosk.command` SSE event; the display
  shell acts on `reload` and `wake` (`shell/kioskCommands.ts`, `DisplayShell.tsx:278-290`).
  `docs/M6-batch-7.md` (not build-ready) extends it to per-screen control from a phone.
- **Sunroom's default port is 7867**, the Host rule answers any `Host` by default (and always
  answers IP literals, `localhost` and `.local`/`.lan`/`.home`/`.home.arpa`/`.internal`/
  `.ts.net` names even when `APP_ALLOWED_HOSTS` locks it; `web/hosts.py:64-77`). CSP is
  `connect-src 'self'` and `frame-ancestors 'none'` (`web/headers.py:19-25`); there is **no
  CORS**, and CSRF needs `X-Sunroom: 1` plus a matching `Origin` on mutations only. Public
  routes: `/api/health`, `/api/version`, `/api/setup/status` (`{setup_complete,
  password_from_env, server_timezone, advertised_url, version}`), `/api/display/state`, the
  pairing routes. The household name is never public. There is no `.well-known` and no
  `/api/discover` route (`docs/NATIVE-APPS.md`, unreviewed, proposes one and an avahi
  `_sunroom._tcp` file written by `install.sh`).
- **Pairing.** `/display` shows a six-character code and a QR of `<advertised url>/pair#CODE`;
  a parent types it under More → Pair a Display; the server sets a 400-day HttpOnly cookie. A Pi
  that runs setup in its own browser becomes a phone, not a screen (ADR 0030), so setup is always
  done from a phone. Settings on the wall is a room (`/settings/$page`, list-and-detail, behind
  the PIN) with the pages Family, Features, Calendars & Accounts, Display, Tasks, Meals,
  Household, Devices, Recently Removed, Backup, Support Sunroom, About.

  CI (`.github/workflows/ci.yml`) is checks only on `ubuntu-24.04`, no secrets, SHA-pinned
  actions, the Playwright report its only artifact.
- **Words (UX §2).** "kiosk" never appears in UI copy. A "screen" is a paired wall screen; a
  "device" is anything signed in with the password. Title Case for buttons of up to five words;

## Research: a Sunroom OS

### What it has to do

For the family (priority 1): plug it in, see Sunroom. Never a terminal, never a keyboard, never
a dead end. For the self-hoster (priority 3): flash a card with Raspberry Pi Imager, or run one
command on a spare machine; updates look after themselves; nothing phones home except GitHub for
updates and their own Sunroom. For us (priority 5): one repo, one design system, one version
number, tested in CI, verified on the owner's Pi with the matrix.

### Recommendation

**Build "Sunroom Screen" as software, and ship the Raspberry Pi image as its packaging.**

- **One agent, `sunroom-kiosk`**, in Python (FastAPI, uvicorn, pydantic; the backend's
  conventions, its own package under `kiosk/agent/`), bound to `127.0.0.1` only. It is the
  launcher and the screen helper rolled into one process, plus: its own setup pages, finding
  Sunrooms on the network, the device actions (restart, shut down, update, Wi-Fi, rotation), the
  browser policy, and a watchdog. The same code runs on the Pi, any Linux desktop, macOS and
  Windows; the platform parts are thin adapters with fakes for tests.
- **The overlay is Sunroom itself.** When the agent launched it, the display shell adds a
  parent-only Settings page, **This Screen**, that calls the agent. When Sunroom can't load (no
  network, no address yet, the server down, a wrong address), the agent's own pages show
  instead: a third shell built from the same frontend (tokens, Lexend, the keyboard, the Sheet),
  so the family never sees a second design language. A page can always get back to Sunroom.
- **The image** is Raspberry Pi OS Trixie Lite plus `rpd-wayland-core`, Chromium, Docker (for
  "Run Sunroom on this screen") and the agent, built by pi-gen in a GitHub Actions
  `ubuntu-24.04-arm` job (free for public repositories since August 2025: 4 vCPU, 16 GB RAM,
  14 GB disk) on every release tag and attached to the GitHub Release as
  `sunroom-os-<version>-pi-arm64.img.xz`. Raspberry Pi Imager flashes it ("Use custom"), with
  Wi-Fi set there or on the screen.
- **The installers** `install.sh` (Linux, macOS, the Pi) and `install.ps1` (Windows) stay at
  their raw-`main` URLs and are also attached to every Release; the owner's short domain can
  redirect to them later. They install `uv`, the agent wheel (checksum-verified), an autostart
  entry and the browser policy, then open the landing page.

### Why not an overlay the app doesn't know about

Three ways to draw "on top of" an arbitrary page were checked and rejected:

- **An iframe wrapper page served by the agent.** Sunroom's session cookie becomes a third-party
  cookie inside a `127.0.0.1` page, `frame-ancestors 'none'` and the service worker fight it, and
  a corner hot-zone would steal touches from the app.
- **A browser extension with native messaging.** Works on every OS, but it is a second artifact
  with its own install path, and it leans on extension privileges to bypass CSP.
- **The compositor.** labwc's manual: "touchscreen gestures are not interpreted by libinput, nor
  labwc"; touch goes straight to the client. There is nothing to hang a gesture on.
- Also rejected: **the agent as a reverse proxy** in front of Sunroom (everything same-origin,
  so no CORS, no CSP change, no local-network permission). It would have to rewrite `Origin` for
  CSRF, forward `Host` and `X-Forwarded-Proto`, carry the SSE stream and multi-GB restores, and
  make the hosted service see every screen as one client address. Hidden complexity for a saving
  of two headers.

The app-as-overlay design costs one Settings page in the display shell, one query parameter and
one route on the server. It also gives remote control from a phone for free later: the server
already pushes `kiosk.command` to the wall; forwarding a `screen` command from the wall page to
the agent needs no new channel (see "Later").

### Browser facts the implementer must respect

- **Local Network Access (LNA).** Chrome 142 (Edge 143) asks permission before a page on the
  public internet calls a private or loopback address (`127.0.0.0/8` counts). The permission can
  only be requested from a secure context. Private-to-loopback requests (a self-hosted Sunroom at
  `http://192.168.…`) are not covered by the first milestone, but Chrome says it will extend the
  rules; and the launcher's `--unsafely-treat-insecure-origin-as-secure` makes that origin
  secure anyway. So the agent **pre-grants** the configured Sunroom origin through managed
  policy: `LocalNetworkAccessAllowedForUrls: ["<origin>"]` and
  `LocalNetworkAccessRestrictionsEnabled: true` (the allowlist names the requesting site, not
  the local endpoint). Where: Debian and Pi OS `chromium` reads `/etc/chromium/policies/managed/
  *.json`; Google Chrome on Linux `/etc/opt/chrome/policies/managed/`; macOS the
  `com.google.Chrome` (or `com.microsoft.Edge`) preference domain, settable with `defaults
  write`; Windows `HKCU\Software\Policies\Google\Chrome` (or `…\Microsoft\Edge`), one numbered
  value per URL. The agent rewrites the policy whenever the address changes. Belt and braces, if a
  later Chrome covers private-to-loopback: the feature behind `chrome://flags/
  #local-network-access-check` can be turned off with `--disable-features=`; read its exact name
  off the target Chromium (`chrome://version` lists active features) before relying on it.
- **CSP.** Sunroom's `connect-src 'self'` would block the wall page's calls to the agent. The
  server widens it for one document only (§T3).
- **`http://127.0.0.1` is potentially trustworthy**, so an HTTPS (hosted) Sunroom calling the
  agent is not mixed content.
- **Chromium policy also silences the browser** (replacing the flags that do it today):
  `MetricsReportingEnabled: false`, `BackgroundModeEnabled: false`, `PasswordManagerEnabled:
  false`, `TranslateEnabled: false`, `DefaultBrowserSettingEnabled: false`, `BrowserSignin: 0`,
  `PromotionsEnabled: false`, `ComponentUpdatesEnabled: false`.
- **Edge** is the Windows default (`msedge.exe --kiosk <url> --edge-kiosk-type=fullscreen
  --no-first-run`); Chrome is used when installed. Edge's kiosk mode is Windows-only; Linux uses
  Chromium or Chrome, macOS Chrome, Chromium or Edge.
- **Chromium's DevTools protocol** (`--remote-debugging-port=0`; the port is in
  `DevToolsActivePort` in the profile) lets the agent see whether the page is a Sunroom and
  navigate it, without touching the app.
- **labwc**: `~/.config/labwc/autostart` (shell), `rc.xml` with `<touch mapToOutput>` and
  `<libinput><device category="touch"><calibrationMatrix>` for rotated touch (the matrices are
  in `docs/KIOSK.md` lines 193-202), `wlr-randr --output <name> --transform 90|180|270` for
  rotation. No kiosk mode and no cursor option in the manual; `labwc-rule.py` already covers
  both.
- **Raspberry Pi Imager** 2.0.0 did not offer customisation for a "Use custom" image (issue
  1943); whether 2.0.11 or later does is **unverified**. The screen's own Wi-Fi page is the
  baseline; Imager's Wi-Fi is a bonus to verify on hardware.

### Finding a Sunroom on the network

Both mechanisms live in the agent and run in parallel for about five seconds:

1. **DNS-SD.** Browse `_sunroom._tcp.local.` (python-zeroconf, no OS service needed). A Docker
   container on the default bridge network can't multicast to the LAN, so the server never
   advertises itself; instead `install.sh` (all on one Pi) writes
   `/etc/avahi/services/sunroom.service` on the Pi (avahi is on Pi OS), and `docs/KIOSK.md`
   shows the four-line file for a self-hoster who wants their NAS found by name.
2. **A LAN sweep.** For each interface, the IPv4 subnet (cap 1024 hosts), `GET /api/discover`
   on ports 7867 (Sunroom's default), 80 and 443 (https), 300 ms connect timeout, 64 in flight.
   Finds the default compose setup; a reverse proxy with name-based routing isn't found, and that
   self-hoster types the address.

Every hit is confirmed with `GET /api/discover` (§T1), which returns `{sunroom: true, id, version,
setup_complete, name, url}`. An older server (no route) is recognised by `/api/setup/status` and
`/api/version` and listed as "a Sunroom" with its version. The screen keeps the `id` of the
Sunroom it was told to use, so when the server's address changes (DHCP), it re-finds it and heals
itself (§T6).

### The agent's API (v1, loopback only)

Every route is under `/api/screen`. Reads are GET; actions are POST with the header
`X-Sunroom-Screen: 1` (so a form can't trigger them). CORS: `Access-Control-Allow-Origin` is
the configured Sunroom origin (and the agent's own), `Access-Control-Allow-Private-Network:
true` on preflights, credentials never. The OpenAPI schema is generated like the backend's
(`sunroom-kiosk openapi`) into `frontend/src/api/screen-schema.d.ts` by `just api-types`.

| Route | Returns or does |
|---|---|
| `GET /api/screen` | `{version, platform: pi\|linux\|macos\|windows, model, session: wayland\|x11\|desktop, capabilities: [restart, shutdown, update, wifi, rotate, brightness, quit, run_sunroom, open_network_settings], sunroom: {url, id, name, found: discovered\|typed\|local}, network: {kind: wifi\|wired\|none, ssid, ip, strength}, update: {check: nightly\|off, state: up_to_date\|available\|installing\|failed, latest, installed}, display: {rotation, brightness_method}}` |
| `GET /api/screen/events` | SSE: `state` whenever any of the above changes; `update.progress {percent, step}`; `discovery.found {…}` while a scan runs |
| `POST /api/screen/restart`, `/shutdown` | Toast first, then the platform call |
| `GET /api/screen/update`, `POST /api/screen/update` | Check now (GitHub tags and the Release's `SHA256SUMS`); install now |
| `PUT /api/screen/update-policy {check}` | `nightly` or `off` |
| `GET /api/screen/wifi`, `POST /api/screen/wifi {ssid, password}`, `DELETE /api/screen/wifi/{id}` | List (ssid, strength, secured, connected), join, forget. `nmcli` on Linux; the desktop capability `open_network_settings` elsewhere |
| `GET /api/screen/sunrooms`, `POST /api/screen/sunrooms/scan` | Last results; start a scan (results stream on `/events`) |
| `POST /api/screen/sunroom/check {url}` | Fetches `/api/discover` (or the older pair) through the agent: `{ok, id, name, version, setup_complete}` or a plain-English reason |
| `PUT /api/screen/sunroom {url, found}` | Save, rewrite the browser policy, restart the browser on the new address |
| `DELETE /api/screen/sunroom` | Forget the address (not the pairing profile); back to Find Your Sunroom |
| `POST /api/screen/run-sunroom` | Sunroom OS only: `docker compose up -d` in `/opt/sunroom`, pulls on first use with progress, then the address becomes `http://localhost:7867` |
| `PUT /api/screen/display {rotation}` | 0, 90, 180, 270: `wlr-randr` now, the autostart block and the touch matrix for next time |
| `POST /api/screen/open {page: sunroom\|settings}` | Navigate the browser (CDP) between Sunroom and the agent's pages |
| `POST /api/screen/quit` | Desktop OSes only: stop the browser and the agent until next sign-in |
| `GET /api/screen/about` | Versions, model, IP, hostname, uptime, the last 50 log lines (never the household name or a password) |

The agent keeps `~/.config/sunroom-kiosk/config` as the source of truth (adding `SUNROOM_ID`,
`SUNROOM_FOUND`, `SUNROOM_UPDATE_CHECK`), so an older uninstaller or a hand edit still work.

### Flows

**First start of a fresh screen (Sunroom OS, or a desktop after the installer).** The browser
opens `http://127.0.0.1:7800/`. The screen shell shows:

1. **Welcome**: the sun mark, "Sunroom", "Let's get this screen set up.", **Start**. (Sunroom OS
   only, and only when Imager set no Wi-Fi and there is no cable:) →
2. **Connect to Wi-Fi**: the networks (name, lock, signal), tap one → the password field with the
   wall keyboard → **Connect** → "Connecting…" → on. A cable showing up skips this. →
3. **Where is your Sunroom?** three cards: **On your network** ("Looking…" with the results as
   they arrive: "The Sample Family's Sunroom · http://192.168.1.20:7867 · version 0.13.0" with
   **Use This Sunroom**; older servers as "A Sunroom · version 0.11.0"); **Run it on this
   screen** (Sunroom OS only: "Sunroom runs on this screen, and the whole family uses it from
   their phones."); **Somewhere else** ("Type the address you were given.", a field with
   `https://` ready, the keyboard, **Check Address** → "That's The Sample Family's Sunroom." /
   "That address isn't a Sunroom. Check it and try again." / "Can't reach that address from
   here."). Also **Look Again**. →
4. **Opening The Sample Family's Sunroom…** (the sun breathing) → the browser goes to
   `<url>/display?dimmer=…&screen=7800` → Sunroom's own pair code, as today. "Run it on this
   screen" shows "Downloading Sunroom… 40%" first, then Sunroom's Welcome with the QR for the
   phone's setup.

**Every day.** Nothing new: Sunroom is on the wall. The agent follows the sleep schedule as the
helper does today, restarts the browser at 03:55, and (Sunroom OS) installs security updates
during sleep.

**Settings → This Screen** (wall only, parent): rows **Network** ("Wi-Fi: HomeNet, strong" /
"Wired"), **Address** ("http://192.168.1.20:7867 · found on your network" or "· typed"),
**Software** ("Sunroom Screen 0.13.0 · up to date" / "0.14.0 is ready" with **Update Now**),
**Updates** (Install overnight / Off), **Rotation** (a Segmented: Landscape · Portrait, Left ·
Portrait, Right · Upside Down; capability `rotate`), and the buttons **Restart**, **Shut Down**,
**Change Wi-Fi**, **Change Address**, **Help** (the About sheet with versions and the address;
"Having trouble? Settings → Support Sunroom"). Toasts repeat the verb: "Restarting…", "Shutting
down…", "Updating… this takes a few minutes", "Joined HomeNet", "Address changed. This screen
is reloading." Restart just does it (a toast and the screen goes dark; low harm). Shut Down and
Change Address confirm in a sheet, because they can't be undone: "Shut down this screen? It
stays off until it's unplugged and plugged back in." → **Shut Down**; "Use a different Sunroom?
This screen leaves The Sample Family's Sunroom and looks for another. Its pairing is kept." →
**Change Address**. On a desktop OS a **Quit Sunroom Screen** button appears (capability
`quit`); on a touch-only screen it never does.

**Can't reach.** The agent's watchdog (CDP, every 30 s: is the page a Sunroom display, is the
renderer alive) and the app's own offline pill cover different cases. The app stays in charge
while it can show something: its "Can't reach Sunroom · showing 9:10 AM" pill and its reload
after a restart. The agent takes over only when the browser shows **no Sunroom at all** for two
minutes (a crashed renderer, a wrong address rendering someone else's site, a server that never
comes back after the nightly browser restart, or a fresh boot with the server down): it navigates
to its **Can't reach The Sample Family's Sunroom** page ("Trying again every 10 seconds…",
**Try Again**, **Wi-Fi**, **Change Address**, **Restart**), and the moment `/api/health` answers it
goes back to Sunroom by itself. Never a dead end: every agent page has a way back, and all of
them return to Sunroom when it is reachable.

**The address moved.** If the Sunroom was *found* (not typed) and `/api/health` fails for two
minutes, the agent scans again for the same `id`; found at a new address, it saves it, rewrites
the policy and reloads (toast on the next page: "Found Sunroom at its new address."). A typed
address is never changed by itself.

### Security and privacy

- Loopback bind only; the Sunroom origin allowlisted for CORS; `X-Sunroom-Screen: 1` on every
  action; actions that change the device confirm in the UI where they can't be undone.
- Privileged work on the Pi goes through one root helper, `/usr/local/sbin/sunroom-kiosk-root`
  (`apt-upgrade`, `write-policy`, `update-sunroom` which runs `/opt/sunroom/update.sh`), allowed
  by `/etc/sudoers.d/sunroom-kiosk` for the desktop user with NOPASSWD and nothing else. Reboot
  and power-off need no root: logind grants them to the active local session. Wi-Fi through
  `nmcli` needs the user in `netdev` (Pi OS's first user is).
- Nothing phones home but GitHub (the update check: tags and the Release's checksums, with a
  `sunroom-kiosk/<version>` user agent; GitHub sees the screen's public address, which the setup
  page says) and the family's own Sunroom. The LAN sweep touches only the screen's own subnets.
- The agent's log never holds a password, the household name or a pair code; `GET
  /api/screen/about` shows the last 50 lines on the wall for Support.
- Sunroom OS has no SSH, no VNC, no default passwords; the first user is `sunroom` with a locked
  password (no `FIRST_USER_PASS`), autologin to the desktop only. Imager's own "Enable SSH"
  customisation still works for people who want it (cloud-init).
- Installers verify the wheel against the Release's `SHA256SUMS`, never read `.env` or any
  secret, and never take a credential on the command line.
- Privacy rule 1 for the repo: `example.com` and the Sample Family in every fixture, test and
  screenshot; the Imager repository JSON and the docs name only the public GitHub and Docker
  Hub addresses.
