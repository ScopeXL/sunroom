# Sunroom 1.0: the plan

> **Status.** Planned on 2026-11-03 from an audit of the app at 0.18.0 (commit `53742e1` plus the
> five fixes of that day, §1), the owner's brief for the first public release, and research on
> how self-hosted apps update and how a Home Assistant integration is built in 2026. Written to
> be executed by an AI session (Opus 5.5) phase by phase, with the owner reviewing at the end of
> each phase and running the hardware pass (F3). The Home Assistant integration has its own plan,
> [`docs/HA-SUNROOM.md`](HA-SUNROOM.md), built in its own repository from the same brief.
>
> **Where this file lives.** `docs/V1.md` until 1.0.0 ships; then it is deleted with the rest of
> the planning journal (Phase D), and the rules it set live on in CLAUDE.md, ARCHITECTURE.md and
> the ADRs. Plans after 1.0 live in `docs/plans/` while they are built (E3).

**How to work through this file.** Phases A to G go in order, except that B (polish) and C
(the API) can be built side by side after A, and D (docs) comes last before G because it
describes what the other phases built. Each task names what it builds, its tests, its docs and
its CHANGELOG line. **The gate per task is the quick one and nothing more** (CLAUDE.md
"Definition of done"): `just quick`, the unit tests the task touched (`just test-fe …`, `just
test-py …`, `just kiosk-test …`), and the one end-to-end spec the task names on one project.
**Never between tasks:** the whole `just e2e`, `just check` or `just screenshots`. The full gate
runs once at the end of each phase (and F5 runs it for the whole plan): `just check`, the whole
`just e2e`, `just screenshots` reviewed against UX §10 for the screens the phase touched, `just
scan`. Commit after each task (`area: summary`, the Co-Authored-By trailer); never push outside
the deploy skill. Hard rules 1 to 10 of CLAUDE.md hold throughout; in particular nothing from a
real household, no name but the Sample Family's, and the private-terms scan before every commit.
Every decision the plan leaves to the owner is in §11 with the default it was written with, so
a session can start without waiting; a different answer changes the task it names.

## 1. The audit, in one screen

Read on 2026-11-03 at commit `53742e1` (0.18.0): every screen, word and handler of the frontend;
the backend's 198 routes, auth, jobs and boot; each install and update path; the 78 Markdown
files and the git history; the review screenshots of every screen at 1920×1080, 1080×1920 and on
a phone. The full findings are in the phases; this is the shape of it.

**In good shape.** The full check is green on the maintainer's machine (1,312 backend, 854
frontend and 294 Sunroom Screen tests; lint, types, the words, the API types, the migrations); the
e2e suite covers the wall, two phones and a laptop with axe, tap targets and the CSP guard. The
wall and the phone look finished: the board reads from across the room, the words hold Title
Case and the family's vocabulary throughout, every sheet has a way back, offline is a quiet pill,
idle brings the board back, the keyboard is right, the empty rooms say the right thing, a paired
screen hides what it can't use (two misses, B3). The backend has no TODOs, one error envelope,
strict security headers, a real SSRF guard with a test that pins it, scrypt passwords, rate limits,
and a boot that refuses rather than corrupts. Sunroom Screen updates itself the whole way, with
the previous version back when a new one doesn't start. Nothing private has ever been committed;
one author; no large binaries in history.

**Fixed today, before this plan** (five commits on `main`, `41701d8` to `d33481d`): the root helper's
`import pwd` that broke every Windows CI run since 0.13.0; the backup race that made the backend
job red; About's sentence naming a button that went in 0.18.0; the "They has" slip; a screen's
one-time pairing secret written to the request log.

## 2. What 1.0 promises

Written for the parent who is not technical and for the homelab person who is, in the order the
app's priorities put them:

1. **Install once.** One line on a Pi or a computer, or one compose file on a server, or one
   click in a NAS's app store. The line never changes (`sunroom.day/install.sh`), it is safe to
   run again, and nobody is asked for a terminal afterwards.
2. **Updates come to you.** Every install hears about a new version the day it comes out, says
   in plain words how it will arrive, and installs it overnight by itself where it can (a screen
   that runs Sunroom, a Pi, a compose file with the updater companion) or with one tap where it
   can't be unattended (About's Update Now, a NAS's Update button). If a new version doesn't
   start, the one before comes back with its data.
3. **The calendar is right**, on every screen and every device, in every household's zone, and
   nothing silently disappears. The e2e suite and the live tests of the integration pin it.
4. **The wall screen never shows a dead end**, never a shell command, never an ID, and says why
   when Sunroom is away ("Sunroom is updating. Back in a minute.").
5. **A program can talk to Sunroom** with a token the family grants and can take back, and the
   family's own devices can control a screen the same way.
6. **The public repository is one clean commit**, with docs that say what Sunroom is, how it
   works, why, and how to change it, and nothing about the people who made it.
7. **Sunroom and its companions** (the Home Assistant integration, the website) are planned and
   released together whenever one needs the other.

## 3. Phase A: install once, updates come to you

The promise 1.0 makes: **the install command is typed once. After that, every part of Sunroom (the
server, Sunroom Screen, the way the screen starts) is brought to each new version by itself, or by
one tap, on every way Sunroom can be installed.** The audit of 2026-11-03 found this true only for
a screen that runs Sunroom itself (On This Computer) and nearly true for an all-in-one Pi; a Sunroom
in Docker on a server never updates itself and the family only hears of a new version if a parent
finds a switch that is off by default. This phase closes every gap.

The design, in one table (what each install does after 1.0):

| Install | Hears about a new version | Installs it | Rolls back | Who sets it up |
|---|---|---|---|---|
| A screen that runs Sunroom (Pi, Linux, Mac, Windows; On This Computer) | This Screen and About, the same night | Overnight by itself (default), or Update Now on the wall; Sunroom comes along | The version before, with its data copy, when the new one never starts | The installer, once |
| A Pi with Sunroom in Docker (`--with-sunroom`, advanced) | The same | Overnight with the screen's update, or Update Sunroom on the wall; a pull that fails is tried again the next night | `update.sh <previous>` by the screen when the new container never turns healthy | The installer, once |
| Docker Compose, Portainer, a NAS (Unraid, CasaOS, Synology), `docker run` | About and Needs Attention, the same day (the check is on by default) | **The updater companion** in the compose file, overnight (default) or Update Now in About; or the NAS's own Update button | The previous tag in `image:` (About says how); a migration means restore first | The compose file or the NAS template, once |
| A browser only (a tablet) | Nothing to update there | The page refreshes itself | n/a | n/a |

Decisions this phase needs from the owner are in §11 (D1 to D5); each has a default so the build
can start.

### A1 The check for new versions is on by default, reads Releases, and reaches the family

- **Backend.** `household.update_check` defaults to true for new households, and one data
  migration turns it on for households that never touched it (a household that chose Off keeps Off:
  the migration sets it only where `update_check` is false and `updates_touched_at` is null; add
  that column, stamped by `PATCH /api/household` when the switch is changed). `core/updates.py`
  asks `https://api.github.com/repos/ScopeXL/sunroom/releases/latest` instead of the tags list: a
  release counts only once its Release exists, so About never names a version whose image and
  files aren't out yet (RELEASING.md's ten-minute window). Keep `SUNROOM_UPDATE_CHECK=0` as the
  server-side off switch. Fix the docstring at `core/updates.py:5-7` (Releases exist since 0.13.0).
- **Needs Attention.** `problems/` gains a core item `update:available` for parents: title "Sunroom
  {version} is out", detail the install kind's sentence (A2), page About. A wall screen sees the
  title only (as backups do today). It clears when the running version is the newest.
- **Words.** About's note stays ("Once a day Sunroom asks GitHub for the latest version. GitHub
  sees your server's address."); the switch reads "Tell me about new versions" with the hint
  "Checked once a day. Turn it off to keep Sunroom from asking GitHub." PRIVACY.md says the check
  is on by default and how to turn it off. Setup doesn't ask: one less step.
- **Tests.** `backend/tests/test_updates.py` (the Releases URL, a pre-release ignored, the default,
  the migration keeps Off), `test_problems.py` (the item, parent-only detail), `AboutPage` unit
  test; e2e `shell.spec.ts` on `display-1080p` (the test server's made-up next version shows in
  Needs Attention).
- **Docs.** DEPLOY.md "Updating", PRIVACY.md, UX §4 About and §8 (the Needs Attention line).

### A3 The updater companion for Docker installs, and Update Now in About

- **Where the version comes from.** The check (A1) reads `https://sunroom.day/version.json`
  (`{"version": "1.0.0", "published": "…", "notes": "https://github.com/ScopeXL/sunroom/releases/tag/v1.0.0"}`),
  written by the site's release bot when a Release is published, with GitHub's `releases/latest`
  as the fallback when the site doesn't answer. Uptime Kuma, Immich and Home Assistant all do
  this: no rate limit, and the only address that sees a household's request is the project's own
  (PRIVACY.md says so). `SUNROOM_UPDATE_URL` overrides it for a self-hoster who mirrors releases.
  Sunroom Screen's updater reads the same file for "is there a newer version" and still fetches
  files and `SHA256SUMS` from GitHub Releases.
- **The companion.** `docker-compose.example.yml` gains a second service, `sunroom-updater`:
  Watchtower as continued by nicholas-fedor (`nickfedor/watchtower`, pinned by digest to the
  release the plan is built with; the original was archived in December 2025 and Nextcloud AIO
  builds its updater from this continuation), with `WATCHTOWER_LABEL_ENABLE: "true"` and the label
  `com.centurylinklabs.watchtower.enable=true` on `sunroom` only, `WATCHTOWER_SCHEDULE: "0 30 4 * * *"`
  (six fields, seconds first; read in the service's `TZ`, which the file sets from the same
  variable as Sunroom's), `WATCHTOWER_CLEANUP: "true"`, `WATCHTOWER_COOLDOWN_DELAY: "24h"` (an
  image younger than a day is left alone, Home Assistant's own safety margin: a bad release can
  be pulled back before any household takes it), `WATCHTOWER_HTTP_API_UPDATE: "true"` with
  `WATCHTOWER_HTTP_API_TOKEN: ${SUNROOM_UPDATER_TOKEN:-sunroom-updater}` and **no published port**
  (the API is reachable only on the compose network), the Docker socket mounted. The Sunroom
  service keeps `read_only`, `cap_drop: [ALL]`, `no-new-privileges` and never sees the socket:
  the companion is the only thing that touches Docker, and a household that doesn't want it
  deletes those lines (the file says so in one comment). Compose `profiles` are not used:
  Portainer's web editor and most NAS importers ignore them, so the companion is plain and the
  comment says how to leave it out. DEPLOY.md's "stricter" variant puts `tecnativa/docker-socket-proxy`
  (`POST=1 CONTAINERS=1 IMAGES=1`, an internal network) between the companion and the socket.
  *First step of this task:* confirm the continuation's HTTP API flags against its current docs
  (the research of 2026-11-03 verified the schedule, label, cleanup and cooldown flags, not the
  API); if the API is gone, Update Now (below) becomes "installs itself tonight" only.
- **Sunroom knows the companion.** Env `SUNROOM_UPDATER_URL=http://sunroom-updater:8080` and
  `SUNROOM_UPDATER_TOKEN` (the compose file sets both from the same variable). When set, About's
  Updates card shows **Update Now** beside "Sunroom {version} is out" (parent-only; the wall
  shows the sentence only), which `POST /api/admin/update` turns into: publish `server.updating`
  on the hub (every page shows the quiet pill "Sunroom is updating. Back in a minute.",
  `StatusLayer`), then `POST {SUNROOM_UPDATER_URL}/v1/update` with the bearer token through
  `core/http.py` (`sunroom-updater` is a container name: the SSRF guard allows that one configured
  host the way the LAN allowlist does). The companion pulls, stops Sunroom, starts the new one;
  pages reconnect, see the new version in the hello and refresh (S2 today). If the updater doesn't
  answer: "Couldn't reach the updater. It still installs updates overnight." and a log line.
- **Overnight.** With the companion, About says "Updates install themselves overnight (about
  4:30 AM), a day after they come out." The wall is asleep then; a screen that is awake shows
  Can't Reach for under a minute and comes back by itself (K1's watchdog) — A6 makes that page
  say why.
- **Tags.** `just image` also pushes the major tag (`1`) beside `1.0.0`, `1.0` and `latest`, so a
  household can pin its blast radius (`image: scopexl/sunroom:1` takes minors and patches,
  `1.0` patches only); the companion follows whatever tag is written.
- **Tests.** Backend: the route (parent, 409 without the companion, the hub frame, the guarded
  call with a fake updater), the config, the `version.json` reader with the GitHub fallback;
  frontend: AboutPage's button and the pill; e2e: none new (the test server has no updater).
  `just smoke-compose` (opt-in, Docker needed): brings up `sunroom` + the companion from the
  example file and checks the companion's `/v1/update` recreates Sunroom on the same volume.
- **Docs.** DEPLOY.md: the companion in one paragraph (what it does, that it needs the Docker
  socket, how to leave it out, how to change the hour, the proxy variant), the Portainer stack
  note; README path b says "updates install themselves overnight". PRIVACY.md: the check goes to
  sunroom.day; the companion talks to Docker Hub only. RESTORE.md's rollback with the companion
  (pin `image:` to the previous version; the companion never downgrades a pinned tag). The site
  repo writes `version.json` on each release (§8, E1's table).

### A4 The Pi paths: retries, rollbacks, the pin, and Update Sunroom on the wall

- `--with-sunroom` and `--server-only` leave the README (D2; KIOSK.md keeps them under "Advanced",
  working as today). What stays must be sound:
- **A pull that fails is tried again.** `_docker_sunroom_behind` is checked from the agent's
  `health_tick` once an hour and at the nightly update, not only at start (`state.py:300`); This
  Screen shows **Update Sunroom** while behind (the old `POST /api/screen/update-sunroom` route gets
  its button back, worded for the all-in-one Pi only).
- **A container that never turns healthy goes back.** `update.sh` records the previous tag and,
  when health doesn't come within 300 s, runs itself with that tag, then prints both outcomes;
  the agent's toast says "Sunroom {new} didn't start, so {old} is back." A migration that already
  ran makes the old version refuse the database (exit 65): `update.sh` then restores
  `/data/backups/pre-migrate/<newest>` first (through `sunroom restore`, the container stopped),
  and says so.
- **A pinned version stays pinned.** `update.sh` with no argument updates to the newest only when
  `image:` has no version or has `latest`; a Pi installed with `--version X.Y.Z` is left alone and
  the agent's hint says "Sunroom here is pinned to {version}" (`sunroom_pinned` in
  `ScreenUpdateOut`).
- `--server-only` Pis get `sunroom-update.timer` from the installer (05:00 daily, `update.sh` with
  the same rollback), unless `--no-auto-update`.
- **Tests.** `kiosk/agent/tests/test_state.py` (the hourly re-check, the button's capability),
  `test_api.py` (the route), a bash test for `update.sh` with a fake `docker` on PATH
  (`kiosk/agent/tests/test_update_sh.py`, running the script with `compose` stubbed: pull fails,
  health fails, pinned tag); `just kiosk-lint`.

### A7 The install line never changes: stable addresses and a rerun that keeps choices

- The documented one-liners become `curl -fsSL https://sunroom.day/install.sh | bash` and
  `irm https://sunroom.day/install.ps1 | iex`, which the site redirects (302) to
  `https://github.com/ScopeXL/sunroom/releases/latest/download/install.sh` and `install.ps1`: the
  released installer, never `main`'s, and no branch name anywhere a family sees. The GitHub
  address is the documented fallback. `INSTALL_COMMAND` (`platform/linux.py`), `$InstallerUrl`
  (`install.ps1`), `uninstall.sh:325`, KIOSK.md, README and the wall's words follow. (The site's
  `_redirects` change is one line in `../sunroom-site`; §8.)
- `install.sh` reruns keep what the wall chose: `write_kiosk_config` reads the previous
  `SUNROOM_ROTATE`, `SUNROOM_SCREEN_HELPER`, `SUNROOM_BRIGHTNESS` and `SUNROOM_OUTPUT` when the flag
  wasn't given (`existing_setting`), so the bare line is always safe to run again. KIOSK.md's two
  contradicting promises become one.
- **Integrity.** `release-assets.yml` adds the kiosk tarball's sha256 (the tag's `kiosk/` as
  `kiosk-X.Y.Z.tar.gz`, built in the workflow) to `SHA256SUMS`, and `install.sh` checks it; uv's

- **Tests.** `kiosk/agent/tests/test_platform_linux.py` (the command), the installer dry runs in CI,

### A8 On This Computer: the start-order race and the rollback that strands a database

- `look_after_local` runs again when `health_tick` learns the local Sunroom's version after a
  start where it was unknown (`state.py:283-300, 690-706`), so a restart that brings the agent up
  before Sunroom never leaves Sunroom behind until the next day.
- `LocalSunroom.update` rolls back only when the new server never started (no `/api/health` within
  the wait) and, when it does roll back after a migration ran, restores
  `backups/pre-migrate/<newest>` first (the program's `sunroom restore`), so the old version
  starts instead of refusing with exit 65. The wait is 10 minutes on a Pi (`uname -m` aarch64 with a
  Pi model file), 5 elsewhere.
- The wall shows the 92 % "Updating Sunroom…" step for the program case too (KIOSK.md and UX §6
  already promise it).
- **Tests.** `kiosk/agent/tests/test_local.py`, `test_state.py`.

### A9 Sunroom Screen's updater: a version that starts but misbehaves can go back

- This Screen → Software gains **Go Back to {previous}** for 7 days after an update (the previous
  wheel is kept beside the current one already), running the apply step with that wheel and its
  setup; the version gone back from is remembered so the overnight update doesn't reinstall it
  until the one after. Words: "Went back to Sunroom Screen {version}."
- **Tests.** `kiosk/agent/tests/test_updater.py`, `test_api.py`; frontend `ThisScreenPage.test.tsx`;
  e2e `this-screen.spec.ts` on `display-1080p`.

## 5. Phase C: connected apps and screens you can talk to

Sunroom's API is cookie-only today: a device signs in with the household password and gets a
session cookie, a screen pairs with a code. Nothing else can talk to it, so a Home Assistant
integration (docs/HA-SUNROOM.md) has no way in, no way to tell one screen from another, and
no way to wake a screen when someone walks into the kitchen. This phase gives Sunroom a small,
safe door for programs, a screens API that the family's own devices use too, and a written API
contract. Every route here is parent-level unless said otherwise, answers the one error
envelope, and sends its sentences with keys (ADR 0043). The backend audit of 2026-11-03 names
the exact files; follow its "where it plugs in" notes.

### C1 Connected apps: a token for programs

- **Model.** A device row of kind `app` (`DeviceKind.APP = "app"`; `devices.kind` is `String(8)`),
  with `token_hash` (an HMAC under a new `KeyPurpose.APP_TOKEN` subkey, as join codes are hashed),
  `token_epoch` (the `auth_epoch` at creation: a password reset or a secret-key change revokes
  every app, as it does every session), `is_parent` (true for every token in 1.0; the column
  exists for scopes later). One migration, with its fixture database.
- **Getting one.** Two ways, both ending in a token shown once:
  1. From a signed-in parent: Settings → Devices → **Connected Apps** → **Connect an App** (a sheet:
     the app's name, default "Home Assistant"; `POST /api/auth/apps {label}` → 201
     `AppTokenOut{device_id, label, token}`), then the token with **Copy** and a QR code that
     encodes it, and the line "Paste it where the app asks. Sunroom shows it only once."
  2. From the app itself with the household password: `POST /api/auth/apps/connect
     {password, label}` (public while a household exists; under `login_limiter` like `/login`;
     8-character minimum already holds) → `AppTokenOut`. This is what the Home Assistant config
     flow uses, so a family types the household password once and never sees a token.
- **Using one.** `Authorization: Bearer <token>` on any `/api` route. `read_token` (`auth/deps.py`)
  accepts it: a constant-time lookup in `AuthState.app_tokens` (loaded with the devices, keyed by
  hash), a `SessionToken` for that device with the live epoch when `token_epoch` matches, no
  cookie ever set on a bearer request, a bad token counted by `login_limiter` per client address.
  `CSRFGuard` skips the header check when `Authorization` is present and no cookie is. The SSE
  stream and the photo files accept it too (both go through `read_token`). `X-Sunroom-Member`
  is honoured for an app as for a screen (an automation that completes "Feed the dog" names
  who did it).
- **What an app may not do**, even as a parent (the same list screens are refused): erase,
  restore, remove or download backups, set or remove the PIN, change the password, create or
  revoke devices or apps, connect sync accounts, run setup, change the language. 403
  `app_not_allowed` "An app can't do that. Do it from a signed-in device."
- **Managing them.** Devices lists Connected Apps (icon, label, "connected 3 days ago", "last
  used …") with **Disconnect** (`DELETE /api/auth/devices/{id}`); `devices.changed` as today. A
  disconnected app gets 401 `app_revoked` and the Home Assistant integration asks to reconnect.
- **Tests.** `backend/tests/test_apps.py` (create both ways, rate limit, bearer on a route, on
  SSE, on a photo, no cookie set, the refusal list, revocation, epoch bump); `test_auth.py`
  (CSRF skip); the migration fixture; frontend `DevicesPage` tests; e2e `shell.spec.ts` on
  `phone-webkit` (Connect an App shows a token once).
- **Docs.** UX §4 Devices and §5 (the sheet), SECURITY.md (tokens are hashed; what an app can't
  do), PRIVACY.md (an app sees what a parent's device sees), ADR (new 0030).

### C2 Screens: state, and commands to one screen or all

- **The wall tells Sunroom what it shows.** `POST /api/screens/me/state` (a screen's cookie
  only) with `ScreenStateIn{room, view, week_offset, day, panel_shown, rail_compact, asleep,
  screensaver, brightness_applied}` whenever it changes, throttled to one post a second (the page
  already keeps all of it in `lib/displayState.ts`). The server keeps the latest per device in
  memory (`state.screens`, not the database; a restart starts empty and screens post again on
  reconnect) and publishes `screens.changed {id}`.
- **`GET /api/screens`** (any session or app) → `ScreenOut[]{id, label, online: bool (a live
  stream for that device), last_seen_at, state: ScreenStateOut|null, display: {screen, brightness,
  reason, awake_until} (from the display state for that screen), agent: {version, capabilities:
  str[]}|null (what the wall reported from This Screen, when it runs Sunroom Screen)}`.
- **`POST /api/screens/{id}/command`** and **`POST /api/screens/command`** (every screen),
  parent or app, body `ScreenCommandIn{command, …}`:
  | Command | Fields | What the screen does |
  |---|---|---|
  | `wake` | `minutes` (default 2, max 120) | Lights up, as a tap does; the page posts `/display/wake` with the minutes |
  | `sleep` | | Goes to Night now, until the next tap or the schedule's morning |
  | `screensaver` | `on: bool` | Starts the photos, or returns to the board |
  | `brightness` | `level` 10..100, `minutes` (default 60) | The panel's light, through the display state (C3); the page's veil when the page dims |
  | `view` | `view: week|rolling|day|month|people|today` | The calendar's view |
  | `room` | `room: calendar|lists|tasks|meals|countdowns|photos` | The rail room |
  | `panel` | `shown: bool` | The Today panel |
  | `rail` | `compact: bool` | The rail's fold |
  | `go_home` | | Home view, this week, filters cleared, sheets closed (what idle does) |
  | `show_event` | `event_key` | The calendar at that week with the event's sheet open (handled at last) |
  | `show_list` | `list_id` | The Lists room with that list open |
  | `show_tasks` | `member_id` (optional) | The Tasks room, that person's column lit |
  | `say` | `text` ≤120, `seconds` (default 8) | A toast on the screen ("Dinner in 10 minutes"); never on phones |
  | `reload` | | The fresh reload it does today |
  `POST /api/kiosk/command` stays one release as an alias of the broadcast route (the old enum
  only), marked deprecated in docs/API.md.
- **Targeting.** The hub learns `publish_to(device_ids, event_type, payload)`: a frame carries
  `to` and the stream writer sends it only to those devices (and the ring replay skips it for
  others), so a phone never sees a screen's command. `kiosk.command` becomes `screen.command
  {command, …}`.
- **The wall.** `shell/kioskCommands.ts` grows a handler per command; `show_event` navigates to
  the event's week and opens `EventSheet` by key; `say` raises a plain toast. A screen that is
  asleep and gets `view` or `show_*` wakes first (2 minutes) and then does it.
- **Tests.** Backend: `test_screens.py` (state posts, online from the hub, targeting, each
  command's validation, the alias); hub unit tests; frontend: `kioskCommands.test.ts` per
  command; e2e `shell.spec.ts` on `display-1080p` (two paired wall contexts; a phone sends
  `view: people` to one; `show_event` opens the sheet; `say` shows the toast).
- **Docs.** UX §4 (what each command does on the wall), §6 "Control a screen" flow, ADR 0030,
  docs/API.md.

## 6. Phase D: the docs a public 1.0 ships with

The repo's Markdown today is a working journal: 13 milestone plans (986 KB) that spell out how the
app was changed, a 191 KB PLAN.md whose milestones section is dated history, a UX.md annotated
with 169 ADR citations and 44 version numbers, 44 ADRs of which 11 are "the owner's Nth notes",
and 118 lines naming Dinner Bell, a private repository nobody outside can read (the inventory of
2026-11-03 lists every line). After 1.0 the history is one commit, so the docs must stand on their
own: what Sunroom is, how it works, why it is the way it is, and how to change it safely. Nothing
in them may describe the maintainer's own setup, name a private project, or carry a date that
only means something to the people who were there.

Rules for every file in this phase: "the maintainer" or no actor at all, never "the owner";
no "Dinner Bell", "Opus", "AI engineer", "UTM", "OrbStack" (except where a build tool is really
